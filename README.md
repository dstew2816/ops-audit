# OpsAudit

[![CI](https://github.com/dstew2816/ops-audit/actions/workflows/ci.yml/badge.svg)](https://github.com/dstew2816/ops-audit/actions/workflows/ci.yml)

An audit of operations automation: it finds the cases an automated procedure never picked up, prices the gap, and ranks the fixes.

![The OpsAudit Overview tab: six result cards](docs/overview.jpg)

*Screenshot of the Overview tab. Live site: https://dstew2816.github.io/ops-audit/*

This is a demo of the kind of work I did at TSMC. Everything is synthetic data, except the clearly labeled public-data check in the Real Data tab.

## The problem

An automated procedure watches for a condition, such as a port blocked for 30 minutes, and acts on it. It runs on live events and cannot replay history. If the platform is down, an event arrives late, or a rule is slightly too narrow, the case is never picked up and nothing records that it was missed.

Success rates are calculated over the cases that were handled. A procedure can report 100% while missing a quarter of what it should have caught.

The people who need the answer are operations and program managers (what is not being caught, what it costs, which fix first) and the automation engineers who maintain the detection logic.

## What is in it

| Tab | What it answers |
|---|---|
| Audit | What should have been picked up, and what was missed? |
| Network | How do batches move between seven stations, and where do they wait? |
| SPC | Is each station in control and capable? Are two stations that should agree drifting apart? |
| Impact | How many labor hours and how much cost does this put at risk, and which fix comes first? |
| ML | Can a model read a messy procedure definition and say what kind of check it is and what it watches? |
| Real Data | Do the process-control and classification methods hold up on a public, real dataset? |
| AI Layers | Can a language model write the detection logic from a document, and group misses by root cause? |

The synthetic data is generated by seeded code, so every run gives the same data: 1,997 rows in 13 tables in an in-browser SQLite database. It includes seven automated procedures, a seven-station route, 1,050 cycle-time readings and one planted six-hour platform outage.

## Results

**Audit.** Seven hand-written queries rebuild what each procedure should have picked up from raw history and compare it with what the procedure logged. Of 92 qualifying cases, 68 were logged and **24 were missed (26.1%)**. A miss means the case was never picked up, whatever happened afterward.

**Statistical process control.** X-bar/R and individuals charts, Cpk and Ppk, run rules, and a chart of the gap between the two parallel Process lanes. Limits come from the first 15 subgroups and are then held fixed. A drift planted at subgroup 15 raised an alarm at subgroup 18; the lane-gap chart caught it at 22. A one-subgroup spike produced exactly one alert. One station has Cpk 1.48 but Ppk 1.18: capable when stable, but it did not stay stable.

**Impact.** Under low, editable assumptions, the 24 misses come to about **17.6 labor hours and $3,618 at risk** in 14 days. The top fix, an outage backfill, covers 8 misses and about half of that ($1,833). The dollar figures are assumptions, not measurements.

**Machine learning.** A decision tree reads a procedure definition and names which of 33 checks it is (queue time exceeded, time since PM, OOC alert left open, hold with no owner, and so on). On 413 held-out records it is right **79.9%** of the time (86.0% on the kind of check). Hand-written branching rules, frozen before training, get 56.4% with English keywords and 66.3% with multilingual keywords. A random forest gets 89.1%. Guessing the most common class gets 2.9%. No single feature gives the answer away: the most important one carries 7.4% of the tree's importance. On deliberately vague records, every method does badly (tree 31.9%).

**Real data (UCI SECOM).** 1,567 production runs with 590 anonymized sensors and 104 failures (6.6%). The result is weak, and the site says so. After the control limits were set from the first 300 runs, 95.0% of failing runs were flagged, but so were 98.8% of passing runs, so a flag says almost nothing about failure. On the later runs, no classifier clearly beats chance (PR-AUC 0.06 to 0.07, against 0.055 for no skill; the test period holds 26 failures). Cpk and Ppk are not reported, because there are no specification limits.

**AI layer 1, documents to detection logic.** Three separate model calls (resolve the procedure, extract the condition, write the SQL), graded against the hand-written queries. In one recorded run, the right procedure was resolved for 5 of 5 documents and 2 of 5 matched the baseline exactly. One document returned 36 rows against 4 because the extraction stage counted from the end of the window instead of from each batch's last event. That error is visible before any SQL exists, which is the reason for the three calls. One document never produced runnable SQL.

**AI layer 2, root-cause grouping.** One model call over the 24 misses, graded against a hand-written diagnosis. In one recorded run it passed 3 of 5 checks. It recovered the outage cluster exactly (8 misses, one cause). It also blamed the outage for a hold that has no time component, and grouped two missed checks that only looked alike.

## Run it

```
npm install
npm run dev                          # the site at http://localhost:5173
npm run check                        # every check below, no API calls
npm run build

python -m pip install -r ml/requirements.txt
python ml/generate_data.py           # the ML dataset
python ml/train.py                   # trains and scores the ML pipeline
python ml/real/download_secom.py     # fetch the public SECOM data (not committed)
python -I ml/real/secom_analysis.py ml/real/data/secom
```

`npm run check` runs `db:check` (the data and the 24 planted misses), `spc:check` (the SPC math and planted problems), `impact:check` (totals reconcile, assumptions move results correctly) and the two scorer self-tests. Each scorer is tested to fail: the self-tests feed deliberately wrong answers through and require them to be rejected. CI runs all of this, plus the build and a fast ML smoke test (`ml/ci_smoke.py`), on every push.

The live AI runs need an API key in your shell (`npm run gen:check -- --save`, `npm run diag:check -- --save`). The site only displays saved results, and the browser never holds a key.

## Where else this applies

An audit like this needs two independent sources anywhere it runs: (a) raw events showing that a condition happened, and (b) the automation's own record of what it did. A silent miss is a gap between the two.

| Domain | The rule | The silent miss | The two sources you'd need |
|---|---|---|---|
| Warehouse inventory | Stock falls below the reorder point, so a purchase order should be created | Stock fell below the point and no purchase order exists | Inventory snapshots + purchase order log |
| Shipping and logistics | A shipment passes its delay threshold, so an exception ticket or customer alert should go out | The shipment was delayed and no ticket or alert exists | Carrier tracking events + ticketing and notification log |
| Quality holds | A hold expires, so the lot should be released or escalated | The hold expired and the lot sat untouched | Hold records + lot movement log |
| Customer service and IT operations | A ticket breaches its service-level target, so it should escalate | It breached and never escalated | Ticket timestamps + escalation log |
| Banking operations | A complaint or dispute passes its response deadline, so it should get a response or escalate | It passed the deadline with no response | Complaint intake records + response log |

Running the audit outside this project means getting both sources and agreeing on the rule's exact definition first; in practice the hard part is access to the automation's own log, not the detection logic. Public datasets rarely include both sources, which is why the audit itself uses synthetic data here, with a separate real-data stress test on the UCI SECOM dataset for the statistical process control and classification methods.

## Limitations

- **Synthetic and small.** 24 misses, 7 stations, one 14-day window, a 413-record ML test set, and one recorded run of each AI layer. The numbers demonstrate a method. They are not a benchmark or a forecast.
- **The answer keys are mine.** The baselines, the diagnosis key, the ML generator, its keyword lists and the hand rules share one author's vocabulary. Real documents would be harder, so the ML accuracy leans optimistic.
- **A smaller ML run came first.** An earlier version with 30 records per type was run once during development. The final version follows a fixed checklist (at least 50 per type, noisier thresholds, a feature-dominance check, a full confusion matrix) rather than anything tuned to test scores. Only the final run is reported.
- **The real-data result is weak.** The SECOM sensors are anonymized and not stable even inside the baseline, there are no specification limits, and only 26 failures fall in the test period, so every interval is wide. A plain individuals chart assumes roughly independent, normal readings; these are neither, and I did not correct for that.
- **The impact model is assumptions.** The labor rate, the chance that a miss causes real cost, and the dollar consequences are illustrative.
- **The AI results are one sample each.** A different run could score differently. The first stage's prompt was changed once before the recorded run, because the API intermittently refused a request to explain its own reasoning. Nothing was changed after seeing scores.

## Built with

JavaScript, React, Vite and SQLite (sql.js) for the app. Python, pandas and scikit-learn for the ML and real-data work. Claude (Anthropic API) for the two AI layers.

I chose the problem and the evaluation rules (baselines and rules frozen before training, a time split on real data, no tuning on test sets). Claude Code, an AI coding assistant, wrote most of the code and drafted the answer keys and hand rules.
